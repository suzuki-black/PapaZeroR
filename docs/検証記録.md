## システム側の軽量化(2026-11-02)

4 面のボス戦で 20 秒、PC を 0.73ms ごとに標本化して内訳を取った(`.rst` のラベルと C の行に対応づけた)。
面のデータではなく、どの面でも通るエンジンの処理を軽くした。

| 処理 | 前 | 後 | 内容 |
| --- | --- | --- | --- |
| 面の裏表と当たり矩形(`faces_draw`、`mesh_draw` の頂点の走査) | CPU の約 20% | 約 11% | C から `face.s` へ。裏表の外積は SDCC の 32 ビット乗算をやめ、MULUW に符号を付ける |
| 傾いた空(`sky_draw`) | 7.6ms | 4.8ms | 多角形 3 枚を全面に重ねる代わりに、境目の 3 本の線の列を行ごとに求めて 4 色を 1 回ずつ塗る(`tilt_rows`) |
| 座標変換(`pt_cam`) | — | 少し軽い | C の呼び出しの手間を省いてアセンブラへ(掛け算は同じ `fmul`) |
| モデルの前処理(`mesh_draw` の視野判定・LOD・変換の準備) | 約 4.6% | ほぼ 0 | C から `face.s` へ。当たり矩形の登録(`hit_add`)だけ C に残した |

4 面のボス戦(同じ 20 秒)は 16.35fps → 18.75fps、描画の中央値は 1 フレーム 44.6ms → 39.6ms。

`mesh_draw` は、エミュレータ上で呼ばれるたびに C の式(16 ビットの桁あふれも含む)で期待値を計算し、実際の結果(捨てたか、LOD 0/1/2 のどれか)と突き合わせた。
4 面と 6 面の 2 万回で食い違いは 0。

PC の標本のうち、0x8A63〜0xA3FF(音のモジュールの外)に出ていたものは、Z80 に切り替えて VRAM へ転送している間の値だった
(openMSX が止まっている R800 の PC を返す)。転送は全体で約 6%、BGM の処理は約 1.3%。

確かめたこと:

- 傾いた空の境目は、Python で厳密な判定(ブロックの中心で `a X + b Y + c > 0`)と 3000 通り比べた。違うのは境目がちょうど中心を通るときの 1 ブロックだけ。
- 通しのスクリーンショットで、空・宇宙・地形・ボスの表示に崩れが無いこと。通しの間、`g_mod` への不正な書き込みは 0。

試してやめたこと:

- 32 ビットの計算を C で書くと(SDCC のライブラリ呼び出し)、空がかえって 13ms に重くなった。行ごとの計算はアセンブラにした。
- `pt_cam` の 9 項を 1 つのループで掛ける形は、R800 ではメモリの読み書きが増えて遅かった。`fmul` を呼ぶ形に戻した。

残っている大きいもの(4 面のボス戦の CPU 時間に占める割合): 多角形の塗り(`raster`・`edge`・`fill`)約 20%、面の振り分け(`face.s`)約 10%、
頂点の変換(`xf.s`)約 8%、VRAM への転送 約 6%、`pt_cam` と `fmul` 約 5%(1 フレーム約 170 回)。どれも中に目立つ山は無く、
多角形と頂点の数に比例して重い。ゲームの処理(`obj_step`・`boss_step`・`objs_draw`)は C の行ごとに 0.6% 未満に散らばっている。

気づいたこと: `mesh_draw` の視野の判定 `lim = z + r * 384` は 16 ビットで桁あふれし、遠くの大きなモデル(半径 61 の地形なら奥 36 単位より先)は
負になって描かれない。結果として描く距離の上限になっているので、アセンブラでも同じ動きにした。

## カメラの補間の桁あふれ(2026-11-03)

背景が「2 歩下がって 3 歩進む」ように見えた。毎フレームの経路の位置とカメラの位置を記録すると、経路は進み続けているのに、カメラは 1 フレームに 28 ずつ進んだあと、約 0.9 秒ごとに 484 戻っていた。

- **原因:** `path_step` が経路の点の間(2 単位 = 512)を `(差 × f) >> 7` で補間していた。f は 0〜127 なので、16 ビットの掛け算が f >= 64 で桁あふれし、点と点の中ほどでカメラが後ろへ飛んでいた。全面のずっと全部で起きていた。
- **修正:** `fmul(差, 2f)`(32 ビットの途中結果)にした。カメラが戻る回数は 0 になった。

直したあと、周回区間から抜けられない面が出た。カメラが飛び跳ねていたおかげで、たまたま見えていた敵があったため。

- 周回は「敵が残っていれば回る」。止まっている敵(`P_HOLD`)が右回りの円の内側にあると、進む向きから 60° 以上横にしか見えず、後ろ 10 単位まで離れることもないので、消えも倒されもしない。
- 経路をなぞって、周回の間ずっと見えない敵を洗い出し(1・3・6 面で 11 体)、外側へ置き直した。一度も画面に入らない敵(2 面と 6 面)も前へ寄せた。
- 5 面のボスはカメラ(高さ 46)より 14 上にあり、画面の上の端に張り付いて部位を狙いにくかった。高さを 50 にした。

## 敵の印と照準(2026-11-03)

どれが敵か見分けにくかったので、元にした TrolleyHomeRun(敵を白く縁取る、照準が敵に重なると赤)を参考にした。縁取りは絵をもう 1 回描くので重く、代わりに次のようにした。

- 敵・敵弾・今のボスの部位の当たり矩形の四隅に鉤(各 3 ブロック)を描く。照準が重なっている敵は赤、補給は緑。
- 照準のスプライトも、敵に重なると赤(バルカンが当たり、誘導弾をロックできる)。
- 最初にロックしたとき、ほかの声が鳴っていなければ「Lock!」。
- 重さは 1 フレーム約 1ms(4 面のボス戦の描画の中央値 38.2 → 39.0ms)。

## ヒナの声(2026-11-03)

大人の女声(flite の slt)の高さだけを 330Hz に上げていたので、男の声に聞こえるという指摘があった。標本化周波数を 1.36 倍と見なして速く鳴らす形にし、声の高さ(444〜500Hz)と声道の響きを両方上げた。読む速さは duration_stretch で戻した。**ゲーム内で鳴らした音は確かめていない**(openMSX の録音が無音になった)。

## 重さと難しさ(2026-11-03)

「重い」「難しすぎる」という指摘を受けて、等速・画面ありで 2 分測った。ゲーム中は実時間でも 19〜20fps で、エミュレータの中の時間と一致した(ホストの遅れではない)。重く感じる原因は fps の落ち込みではなく、次のものと見て直した。

| 原因 | 対策 |
| --- | --- |
| 4 ティックかかる枚(1 面の道中で 6%、地形が平均 31ms) | 地形の細部を省き始める距離を 1 区画手前に(4 ティックの枚 6% → 3%) |
| 照準が描画(20fps)と一緒にしか動かない | 照準だけ毎ティック動かす。描画の合間と表示待ちに入力を読み、垂直帰線の割り込みがスプライト 0 の位置(2 バイト)を書く。本体が VDP に触らない間(`g_spr_live`)だけ |
| 照準が遅い(1 ティック 1〜2 ドット) | 2 → 4 → 6 ドットに加速(端から端まで約 0.7 秒) |
| 飛ぶのが遅い(速度 20 で 1 秒 5 単位) | 2 倍。オープニングは約 60 → 30 秒、各面は 85〜115 秒 |
| オープニングを飛ばせると分からない | 「SPACE: SKIP」を点滅表示 |
| 遠くの敵に当たらない | 照準の当たりを 3×3 ブロックに |
| 速くした分、敵の弾が増える | 撃つ間隔を約 1.5 倍(`st` は u8 なので 240 まで) |

速くすると、ボス(カメラの前へ毎フレーム 1/8 ずつ寄る)が遅れて近づき、大きく描かれて 6 面のボス戦が 16.2fps まで落ちた。カメラの動きを先に足してから寄せる形にして戻した。

ついでに見つけた不具合: 計器は 1 フレームに 1 項目ずつ書くが、レーダーが高度の番を奇数フレームに横取りしていた。撃ち続けて過熱のバーが毎フレーム変わると、高度の番がいつも奇数フレームに当たり、高度が一度も表示されなかった(自動プレイでは出ない)。レーダーに専用の番を割り当てた。

ページ 0 の空きは 25 バイト。C をページ 0 に足す余地はほぼ無い。

## 隠しコンフィグ・オープニング・曲(2026-11-03)

- **隠しコンフィグ:** 9 項目を 3 行おきに描いていて、高さ 5 行の字が重なっていた。6 行おきに 6 項目を出し、選んだ項目に合わせて送る形にした。下の帯にタイトルの絵が残っていたので、計器の絵を読み込んで黒帯にする。
- **オープニング:** 零戦を道のり 104 に置き、カメラが 142 まで進むので、走り寄った零戦を通り過ぎていた。零戦を道の終わりのすぐ先(146、高さ 3.5)に置き、乗り込むところで場面が終わる形にした。
- **ページ 0 のあふれ:** 上の修正でページ 0 が 95 B あふれ、常駐部の先頭(0x4000-)に重なった。mkrom はあふれた分を常駐部のアドレスとして数えていて止めなかった。常駐部も 0x8000 を超えた分を黙って落としていた。両方を長さで確かめて止めるようにし、レーザーの描画を HICODE(`game_ai.c`)へ移した(ページ 0 は 15240 / 15872 B)。
- **曲:** 全体に明るすぎるという指摘を受け、全 15 曲を、娘を救いに一人で向かう 80 年代のアクション映画のような曲調(短調、刻むベース、軍隊風のスネア、金管)に書き直した。旋律はオリジナル。曲は 12253 / 12544 B。**FM の音色はレジスタの値から作ったもので、誰も聴いていない。**

## 上限を 30fps に(2026-11-04)

`present` が毎回 3 ティック待っていたので、描き終わっていても 20fps より速くならなかった(TrolleyHomeRun は 2 ティックで、上限 30fps)。
ゲームの本体の表示だけ 2 ティックまで縮めた。継ぎ目・ゲームオーバー・隠しコンフィグなど、フレームで数える場面は 3 ティックのまま。

- **フレームで数えていた演出:** 点滅、ボスの揺れ、機動(ロール・ループ・急降下)、演出のロール、画面の揺れ、被弾の光、エンディングの色の移り、ファイバーの掃き、デモの長さ、なぞってロックする間隔。
  3 ティックで 1 進む時計(`g_anim`)とその枚の進み(`g_an`)で数えるようにした。20fps で回っている間は前と同じ動きになる。
- **変える前の見込み:** 1 周期の仕事(計器の書き込み + 転送 + 計算 + 描画)を毎フレーム測ると、33.3ms に収まる枚は全体の 43%(1 面の道中 13%、ボス戦 0〜20%)。
  実際には見込みより速くなった(下の表)。

オープニングからエンドロールまでを 1 回で通した(自動プレイ、ダメージなし、`Panasonic_FS-A1ST`)。表示の切替の間隔から数えた。g_mod の書き込みの検査で破壊は 0 件。

| 場面 | fps | 2 ティックの枚 | 3 ティック | 4 ティック以上 |
| --- | --- | --- | --- | --- |
| オープニング | 25.7 | 68% | 29% | 3% |
| 1 町 道中 / ボス | 23.5 / 23.6 | 55% / 50% | 38% / 47% | 7% / 2% |
| 2 港 道中 / ボス | 23.2 / 23.4 | 51% / 52% | 45% / 45% | 4% / 3% |
| 3 峡谷 道中 / ボス | 23.2 / 21.0 | 52% / 17% | 42% / 71% | 6% / 11% |
| 4 雲海 道中 / ボス | 26.9 / 22.4 | 80% / 39% | 19% / 58% | 1% / 3% |
| 5 成層圏 道中 / ボス | 27.0 / 25.2 | 79% / 75% | 21% / 24% | 0% / 1% |
| 6 軌道 道中 / ボス | 27.2 / 23.6 | 81% / 48% | 19% / 47% | 1% / 5% |
| エンディング | 28.1 | 90% | 10% | 0% |

1〜3 面とボス戦は 2 ティックと 3 ティックの枚が半々に混ざる。動きは経過時間で進めているので速さは変わらないが、ぎくしゃくして見えるかもしれない。**手で遊んでの見え方はまだ確かめていない。**

- **誘導弾:** 速くなって敵を狙いにくいという指摘を受け、最大 6 発(開始 3 発、補給 +2)から、面ごとに 500 発(補給 +50)にした。計器は棒 6 本から 3 桁の数字に。通しプレイで破壊 0 件。

## ロックの作り直し(2026-11-04)

アフターバーナーII の遊び方(攻略記事などで確かめた範囲。ゲームの中の数値は見つからなかった)にならい、作者の指定で次の形にした。

- 照準を敵に重ねるだけでロックする(前は A を押したままなぞる)。ロックで「ピピ」。8 体まで。照準が外れても 60 ティック残る。
- B を押すたびに 1 発、古いロックから撃つ。撃った敵はロックから外れ、その誘導弾が飛んでいる間は再びロックできない。ロックが無いと、進む向きへまっすぐ飛んで 1 秒で消える。
- 撃つたびに「Fire!」。続けて撃つと前の Fire! を切って頭から言い直す(ほかの声が鳴っている間は割り込まない)。
- 声のモジュールは 16KB で、Fire! を足すと 1.1KB あふれた。ロックの声を使わなくなったので、Lock! の枠を Fire! にした(オープニングの Lock! も無くした)。
- まっすぐ飛ぶ処理を `obj_step`(HICODE)に書くと、`obj_step` が約 840 B 膨らんで HICODE があふれた。数行の関数にしてページ 0 に置いた。
- 自動プレイも、ロックがあれば誘導弾を撃つ(デモと試験)。2 面で、ロックせずに撃った 2 発が 1 秒で消えること、ロックして撃つこと、補給で 500 までに戻ることを記録で確かめた。通しプレイで破壊 0 件。

**声と fps:** 声を鳴らしている間は、転送で Z80 に切り替えられない(`pcm.s` の冒頭)。自動プレイはボスの部位へ撃ち続けるので、Fire! がほぼ鳴りっぱなしになり、ボス戦が大きく落ちた。3 面から始めて、声を止めた場合と比べた(声を止める以外は同じ)。

| 場面 | 声あり | 声なし |
| --- | --- | --- |
| 3 面 道中 / ボス | 23.7 / 15.5 | 24.4 / 19.9 |
| 4 面 道中 / ボス | 25.8 / 16.7 | 26.5 / 21.3 |

Fire! を半分の速さで読ませ、0.30 秒から 0.15 秒にした(声のモジュールは 15577 B)。同じ測り方で、3 面 道中 / ボス 23.8 / 17.0、4 面 25.5 / 18.5。
自動プレイは 0.2 秒ごとに撃つので、声はまだ 7 割ほど鳴っている。手で撃つ間隔が長ければ、落ち方はこれより小さい。**短くした声は誰も聴いていない。**

- **ロックの枠:** 照準(3×3 ブロック)を敵の小さな枠に重ねないとロックできず、爽快感が無いという指摘を受けた。照準のまわりに横 24 × 縦 16 ブロックの枠(水色の四隅)を描き、
  敵の当たりの矩形が少しでもかかれば、かかった敵をまとめてロックする(8 体まで)。実時間で 2 面を照準を振るだけで遊ばせ、枠の端にかかった敵がロックされる(赤い印)ことを画面で確かめた。
  ページ 0 は 15620 / 15872 B。
- **Fire! の高さ:** 低すぎるという指摘を受け、ヒナの声と同じく標本化周波数を 2 倍と見なして、声の高さと響きを両方上げた。
  rms の声は高さを 240Hz と指定しても 115Hz ほどで頭打ちになった。自己相関で測ると、85Hz から約 220Hz(語尾は 150Hz)。長さは 0.15 秒のまま。**誰も聴いていない。**
- **1 面の速さ:** 低く飛ぶ面で、ロックした戦車へ誘導弾が届く前に通り過ぎ、倒したか見えなかった。1 面だけ速さを 20 → 14(ボスの周回は 16 → 13)にした。
  通しプレイで 1 面は 100 → 125 秒(ボス戦を含む)。ほかの面は変えていない。破壊 0 件でエンドロールまで通った。
- **被弾の揺れ:** 揺れていたのは下の計器盤(約 0.4 秒)と、画面の傾き(被弾から 4 ティックだけ)で、ゲーム画面はほとんど動いていなかった。
  上の画面の R#18 を `g_r18_top` にして、計器盤と同じく分割のたびに書く(横だけ。縦にずらすと分割の行も動く)。初めは 6 ドット、あとは 3 ドットで左右に約 0.5 秒。傾きも左右に振る。
  面を抜けるときに両方 0 に戻す。実時間の画面で、被弾の直後にゲーム画面が横にずれることを確かめた。
- **Fire! をもっと高く:** 見なしの倍率を 2 → 2.6 に。測ると約 290Hz(語尾は 200Hz)。**誰も聴いていない。**
- **敵が壊れるとき:** 爆発はあったが 16 ティック(0.27 秒)で、遠くでは 3 ブロックほどしかなく、倒したのが見えなかった。28 ティックに延ばし、
  遠くでも 2 ブロックより小さくせず、破片 4 つを放物線で飛ばす。爆発の描画は約 1.2KB になり、HICODE にもページ 0 にも入らないので、
  新しい `fx.c` に分けて常駐部に置いた(常駐部 15930 / 16384 B)。通しプレイの fps は前と変わらない(面ごとの平均の差は ±0.5、6 面のボスだけ 18.3 → 17.1)。破壊 0 件。
- **ロックが外れる:** ピピのあとすぐロックが外れることがあり、ストレスだという指摘。撃った敵をロックから外し、その誘導弾が飛んでいる間はロックし直さない作りだったので、
  撃つと赤い印が消えていた(前の指定の「すでに飛んで行った相手」を「誘導弾が向かっている敵」と読み違えた。「通り過ぎた敵」の意味だった)。
  撃ってもロックは外さず、B を押すたびにロックした敵へ順に撃つ(3 体なら A → B → C → A → B → C)。外すのは、時間切れ(枠を出て 60 ティック)・倒した・
  進む向きで自機より後ろへ行ったとき。2 面の自動プレイの記録で、撃つ順番が回ること、枠を出たあと残りが 52 → 4 と減りながら撃ち続けて 1 秒で外れることを確かめた。
- **ロックしているのに誘導弾が飛ばない敵:** 照準が重なった敵はロックしていなくても赤い印になる。そこへ、8 つの枠が埋まっていると新しい敵をロックしない作りが重なった。
  埋めていたのは、枠を出て残っているだけのロックと、撃っても効かないボスの部位(登場中・飾り・まだ開いていない組・ヒナのカプセル)。
  これで、赤いのに一発も向かわない敵ができていた(カプセルへ撃てば自機が傷つくところだった)。ロックできるのを今撃てる部位だけにし、満杯のときは枠を出て残っているだけのロックのうち
  一番古いものを新しい敵に譲るようにした。3 面と 6 面のボス戦の記録で、ロックに入るのは今の組の部位だけ(6 面の第 2 の組は開いてから)、登場中は 0 件を確かめた。
  通しプレイはエンドロールまで、破壊 0 件。
- **飛ぶ高さ:** ずっと低く、地上の敵ばかりという指摘。筋書きでは、1 面(町を制圧した部隊を低空で蹴散らす)と最終面以外は追っ手との空中戦が主になる。
  前は 2 面 9〜15、3 面 7、4 面 12、5 面 14 から上昇で、2・3 面は敵の半分以上が戦車だった。
  - 2 面: 前半は高さ 24 で戦闘機と空中戦。後半に港の基地へ降り(10)、レーザー戦車を叩いてボスへ。
  - 3 面: 前半は谷の上(28。壁は 24 まで)で空中戦。後半に谷へ降り(7)、谷底の基地とボスへ。上から見た谷は台地の割れ目に見え、破綻しない。
  - 4 面: 雲の峰(18 まで)の上を飛ぶよう、全体を 8 上げた(20)。5 面も全体を 8 上げた(22 から 54 まで)。
  - 1 面と 6 面はそのまま。区間の長さは変えていないので、敵の出る位置・周回・ボスの位置は前と同じ。
- **敵の名前の札:** 遠くの敵は SCREEN 3 の粗さでは何かわからないという指摘から、零戦の画像認識という体裁で、敵の横に名前の札をスプライトで出す。
  - SCREEN 3 のスプライトは横に 4 枚まで・1 枚 1 色・常に手前。札(スプライト 1〜6)は上下 32 ドット以内に札が 3 枚あれば置かず、
    敵の高さから ±32・±64 ドットずらして置く。照準と合わせて、どの走査線でも 4 枚以下なので札は消えない。
  - 引き出し線もスプライト(横・「/」・「\」の 3 つの絵、12 枚)。札のあとの番号で、毎フレーム順番を回すので、4 枚を超えた行では線だけが交代で消える(ちらつく)。
  - 選ぶ順は照準の敵 → ロックした敵 → 近い順で、6 つまで。名前は 4 字 2 行まで(P-51、TANK、LASR/TANK、AIR/SHIP など)。ボスの部位と弾には付けない。
  - 属性の転送は 17 → 77 バイト(19 枚)。スプライトの絵(17 枚、544 B)はページ0から外し、コクピットの絵のバンクの後ろに置いて cockpit_load で VRAM へ送る。
  - ページ0が約 2KB あふれたので、札の処理を詰め、自動プレイの入力と照準の敵探しを HICODE へ、パレットの補間を常駐部へ移した
    (HICODE 7121 / 7168、常駐部 16225 / 16384、ページ0 15688 / 15872。どこもほぼ満杯)。
  - 2 面・3 面の実時間の自動プレイで、札が最大 5 枚、上下に互い違いに並び、線が敵を指すことを画面で確かめた。
  - 通しプレイはエンドロールまで、破壊 0 件。道中の fps は 0〜0.9 下がった(2 面 23.4 → 22.5、4 面 25.6 → 24.9 など)。ボス戦はほぼ同じ。
- **敵弾を撃ち落とせない(1 面のボスが倒せない):** 回避の手段が無いので、無敵でないと 1 面のボスが倒せないという指摘。
  Starblade・Panzer Dragoon など同系のゲームは、自機で避けるより敵弾を撃ち落とすのが基本の守りになっている。
  1 面のボスは 2 秒ごとに砲弾を 1 発撃ち、砲弾はバルカン 1 発で壊れるが、無敵なしの自動プレイでは全弾が当たり、ボスが出て約 10 秒で体力 5 が 0 になった。
  毎フレームの記録で見ると、砲弾が狙うのは自機の位置そのものなので、近づくほど画面の端へ流れ、映っているのは撃たれた直後の 4 フレームほどだった。
  - 敵弾の狙う先を自機の前 4 単位の点にした。弾は画面の真ん中へ向かって大きくなりながら飛んでくるので、撃ち落とせる。
  - バルカンは照準の下の一番手前の物体に当たるが、そこに自分の誘導弾が入り、誘導弾を壊していた(自動プレイも自分の誘導弾を狙っていた)。
    誘導弾には当たり矩形を作らないようにした。
  - 無敵なしの自動プレイで、1 面のボスを被弾 0 のまま約 10 秒で倒した。1 面から続けると 5 面のボスまで進み、そこで体力が尽きた
    (5 面のボスはミサイルとレーザーを使う。レーザーは撃ち落とせず、撃つ部位を倒して止めるしかない)。
  - 無敵ありの通しプレイはエンドロールまで、破壊 0 件。fps は前とほぼ同じ(道中 22.6〜26.6、ボス戦 15.7〜18.4)。
- **ビルドの Python:** 環境の `python3` が 3.15 になり Pillow が無かったので、`make PYTHON=python3.14` で作った。

## オープニングの作り直し(2026-11-08)

- **何の場面かわからない:** 前のオープニングは経路に沿ってカメラが進み、道ばたに小道具を置くだけで、人も機体も動かせなかった。
  ヒナは一人で空へ上がっていき(さらわれたのではなく、宇宙人に連れ去られたように見えた)、零戦は白い胴に板の翼でセスナ機に見えた。
- **時刻で動く映画にした:** オープニングだけ、カメラと役者(人物・機体・小道具)のキーフレームを、場面の始めからのティックで補間する
  (`src/engine/op.c`、台本は `tools/stage_data.py` の `opening()` が `film.h` に書く)。曲も同じ 60Hz のティックで進むので、絵と曲はずれない。
  - コードの置き場所: ページ0・常駐部・HICODE はどこも満杯なので、オープニングのモジュールの中身の後ろ(0x93C0〜)に置き、
    モジュールの見出しの `hook` から呼ぶ。モジュールは ROM のまま見えるので変数は持てず、出来事の番号は本体の `ev_i` を借りる。
  - 筋: 制圧された町(戦車・飛行船・黒煙)→ 朝の農場でヒナが遊ぶ → 父が家のほうを見た隙に、戦闘機が家の上をかすめて道へ降りる →
    振り返ると 1 人目がヒナを担いで走り、2 人目が父に銃を向ける → ヒナをカプセルに入れて飛び立つ → 父は零戦へ走り、乗り込み、離陸して追う。
  - 曲: 頭に 4 小節(不穏な町・のどかな農場)を足した。10 小節目のスネアのロールで乗り込み、テンポが上がる 11 小節目で計器盤が出る。37.3 秒。
- **零戦:** A6M の公開されている寸法(全幅 12m、全長 9.06m、上反角 6 度)から作り直した。黒いカウリング、低翼、長い風防、丸い翼端、尾輪式で尻を下げた駐機姿勢、日の丸。
  - 濃緑の上面は草地に溶け、明灰の下面は朝の空の橙に溶けたので、上面は初期型に近い明灰(飴色)、下面は濃い灰にした。
  - 格納庫の中に置くと目の高さの真正面からしか見えず、主翼が線になったので、納屋の前の外に止め、斜め前から横顔を見せる。
- **人物はスプライト:** 64×40 のブロックでは人が数ブロックにしかならず、娘と誘拐犯の見分けがつかなかった。
  オープニングは操作も敵の名前の札も無いので、人物・誘拐の戦闘機・戦車を 2 枚重ねの拡大スプライトで描く
  (誘拐犯は黒 + 灰、ヒナは赤 + 白、戦闘機は黒 + 白いカプセル、戦車は灰 + 黒)。近さで大・中・小の絵を選ぶ。
  - 1 枚目(形)を 1〜8 番、2 枚目(色)を 9〜16 番にした。横に 5 枚以上並ぶと消えるのは色の 2 枚目だけで、形は残る。
  - 毎フレーム全部を隠してから置き直していたら、その途中で割り込みが属性を VRAM へ送ったフレームは何も映らなかった。置いてから余りを隠す。
  - 戦闘機は中の大きさの絵だと黒い塊になり、戦車で逃げたように見えた(作者の指摘)。遠くまで大きい絵で描く。
  - スプライトのパターンは 63 / 64 枚。
- **タイトル → デモでタイトルの絵が化けて残る:** スプライトの絵を足して、cockpit_load が一度に送る量が 544 → 1120 バイトになったら、
  タイトルからデモ・オープニングへ移った後の数秒、上の画面が下の画面のモードで出た(タイトルの絵が化けて見えた。作者の指摘)。
  量を元に戻すと消えたので、帰線の直後に 4 回に分けて送る形にした。タイトル → デモの経路でも化けないことを画面で確かめた。
- **容量:** オープニングのデータ 5048 B と演出のコード 3323 B(モジュールの 9216 B のうち)。人物・戦闘機・戦車のモデルを外して空けた。ページ0は 15857 / 15872 B。
- 無敵ありの通しプレイはエンドロールまで、破壊 0 件。オープニングは平均 16.4fps、ほかの面は前とほぼ同じ。

## 見つけた不具合

- **主記憶の大きさ:** 256KB は 16 セグメントなのに、面のデータをセグメント 16〜23 に置いていた。256KB の機種では折り返してエンジンを壊し、ゲーム中に暴走した。512KB に改造した機種定義では起きないので気づかなかった。今の面と次の面だけをセグメント 1・5 に置き、継ぎ目で読む形にした。
- **SDCC の生成コード:** `--opt-code-size` で、16 ビットの引き算が `ld l, a` のあとに `inc hl` して別の番地を読むコードになり、区画の番号が壊れた。周回の長さを先に計算して変数に持つ形で回避した。
- **分割のやめ方:** IE1 を立てたまま `g_split` を 0 にすると、FH が落ちず割り込みが入り続けて固まった。`split_off` にまとめた。
- **VRAM の書き込み:** 垂直帰線の割り込みがスプライトの転送で番地を変えるので、計器と字幕は切替の予約が無い間だけ書く。
- **向き:** `視線の向きの不具合_TrolleyHomeRun向け.md` を参照。
